Discovered while fixing the 9/8 and 9/13 diary gaps and the worktree project naming. Not done; Saqoosha picks.

## 9/8: Gemini 503 is a hard failure

The 04:05 run on 9/9 regenerated twice for missing sections, then the third Gemini call returned `503 UNAVAILABLE` and the CLI exited with `Error: Gemini error (503)`. There is no retry with backoff at the API layer, and the LaunchAgent does not re-run on failure. One transient 503 loses the day.

Options: retry 503 / 429 inside `GeminiAPIService` with a short backoff (three attempts, 30 s apart), or fall back to a second provider on 5xx, or have the LaunchAgent re-fire at 05:00 with `--skip-existing`.

## 9/13: both Studio jobs died without exiting, and stdout left no trail

`daily-generate.err.log` shows `Cursor reader exceeded 120s timeout for 2026-09-13; skipping` at 04:07 and nothing after; `daily-generate.out.log` has no `Aggregating 2026-09-13...` line at all, and the Studio's `push-stats` run for 9/13 left nothing either (no host-stats row on the cloud). The Studio was rebooted at 11:44 on 9/14. No crash report exists.

Two separate points:

- **stdout is fully buffered when launchd redirects it to a file.** Swift `print` to a non-tty buffers until exit, so a process killed mid-run leaves an out.log with no evidence it ever started. `setvbuf(stdout, nil, _IOLBF, 0)` at CLI startup (or `fflush(stdout)` after progress prints) would make the log honest.
- **The Cursor timeout is reported, not enforced.** `runWithTimeout` cancels the task group, but the SQLite scan inside `CursorService` is not a cancellation point (documented caveat in `AggregatorService`). After the timeout fires, the group still waits for that child, so the process can sit for hours with the timeout already printed. The exact reason the 9/13 run never finished is not proven; this is the mechanism that fits the evidence.

## Studio: xcodebuild is broken since the Tahoe 26.6.2 update

`xcodebuild` on the Mac Studio fails to load `IDESimulatorFoundation` (`Symbol not found: _$s12DVTDownloads...`) and asks for `xcodebuild -runFirstLaunch`. That needs admin auth in a GUI session. Until then nothing can be built on the Studio, including `install-daily-launch-agent.sh`. The regeneration on 9/15 used a binary built on the MBP and copied over.

## Old per-worktree names persist in caches and cloud rows

The worktree fix changes names at read time only. `~/Library/Caches/CCDiary/statistics/` on both Macs, the cloud `host_stats` rows, and the `diaries.stats` columns for past dates still carry one project per worktree (inflated `project_count`, `top_project` = a branch name). Fix is `rm -rf ~/Library/Caches/CCDiary/statistics/` on each Mac, then `push-stats --date` for the affected dates and `sync-cloud --merge-cloud-stats --compute-stats` on the Studio.
